# 简历优化与判断（Resume Review）

## 适用场景

- 判断一份简历写得好不好、能打多少分、问题在哪。
- 已有简历，要针对某个岗位 JD 改写 / 定制。
- 投递前做最后一轮检查。

用户只要诊断时，走路径 A，不要顺手覆写简历；用户要出成品或按 JD 改，走路径 B。

## 材料从哪来

- 主简历：`resume_read`
- 岗位定制稿：岗位会话用 `job_tailored_read`；简历会话用 `resume_tailored_read`（传 jobId）。
- 岗位 JD 与匹配度报告：岗位会话用 `job_info` 读全文。简历会话没有读 JD 的工具，请用户把 JD 贴进来，或让他去该岗位的工作台会话。
- 岗位列表与匹配度摘要：`job_list`。
- 上传的旧简历、作品集：`upload_list` → `upload_read`。
- 简历会话写定制稿要用 `resume_tailored_write` 并传 jobId；岗位会话的 `job_tailored_write` 已锁定当前岗位。

## 路径 A：简历评分与诊断

### 1. 先判方向

技术 / 产品 / 运营 / 市场 / 销售 / 财务 / 人力 / 设计 / 教育 / 医疗 / 法律 / 制造……，并按方向调整维度口径：

- 技术岗：「专业深度」看技术栈分层、系统复杂度、工程实践；「影响力」看 GitHub、开源、技术分享。
- 非技术岗：「专业深度」看方法论、案例复杂度、业务结果；「影响力」看作品集、公开分享、行业资源，**不要因为没有 GitHub 扣分**。
- 应届生：「工作经历」看实习与项目质量，不拿全职年限作硬门槛。

### 2. 七维打分（100 分）

| 维度 | 满分 | 看什么 |
| --- | --- | --- |
| 基本信息完整性 | 15 | 姓名、电话、邮箱、城市、求职意向；相关链接 |
| 成果量化程度 | 25 | 数字、百分比、规模、前后对比；强动词；业务影响 |
| 专业深度与广度 | 20 | 技能分层、案例难度、方法体系、工具链 |
| 工作经历质量 | 20 | 公司 / 项目可信度、职责深度（主导 vs 参与）、成长轨迹 |
| 教育背景 | 8 | 学历、学校、相关专业、论文 / 课程 |
| 个人影响力 | 7 | 开源、作品集、论文、演讲、行业证书、公开分享 |
| 表达能力 | 5 | 结构清楚、格式统一、无套话、无冗余 |

逐维评分时按证据判断，不要机械数关键词：

- 出现「参与」「配合」「协助」「做一些」：对应条目按参与度降权，不整份简历一刀切。
- 通篇没有数字：成果维度按上限的 40%-60% 给，不直接给 0。
- 技能平铺、没有分层：专业维度按 60%-75% 给。
- 自我评价是「认真负责、学习能力强」这类套话：表达维度扣分，但不影响其他维度。
- 有硬性缺口（学历、年限、证书）：在结论里单列，不用总分掩盖。

评分要克制，宁低勿高。用户拿这个分数去比较时，明确说明这是对话里的诊断分，和岗位表的后台「简历评估」「完整性」不是同一口径，也不代表真实 HR 的通过率。

### 3. 输出

```
## 简历诊断：XX / 100

一句话结论（最匹配什么岗位，最大问题是什么）。

| 维度 | 得分 | 依据 |
| --- | --- | --- |
| 基本信息完整性 | X / 15 | … |
| 成果量化程度 | X / 25 | … |
| 专业深度与广度 | X / 20 | … |
| 工作经历质量 | X / 20 | … |
| 教育背景 | X / 8 | … |
| 个人影响力 | X / 7 | … |
| 表达能力 | X / 5 | … |

### 最值得先改的三件事

1. …
2. …
3. …

### 改写示例

- 原句：「…」
- 改写：「…」（只改表述，不新增事实）

### 还需要你确认

- …
```

改写示例最多给 3 条；用户要更多再逐段展开，不要一次把整份简历重写掉。

## 路径 B：按 JD 定制

### 步骤 1：收齐材料

- JD 全文（用户贴、`job_info` 读、或让用户先建岗位档案）。
- 当前简历（主简历或已有定制稿）。
- 目标公司类型（大厂 / 中小 / 初创），决定侧重点。
- 用户的硬约束：城市、薪资、是否接受降级 / 转岗。

材料不全时先列缺口，能基于现有信息做的先做，不要空等。

### 步骤 2：拆 JD

按 `references/jd-analysis.md` 提炼：

- 核心职责（这个岗位每天做什么）
- 硬性要求（学历、年限、技能、证书、行业经验）
- 软性要求
- 项目经验偏好（规模、类型、角色、成果口径）
- 分级：基础必备 / 进阶加分 / 差异化竞争

只有一条 JD 时，就按这一条拆，不要假装做了「多平台大数据分析」；需要更多样本时可以问用户要不要再贴两条同类 JD。

### 步骤 3：匹配诊断

按 `references/matching-diagnosis.md` 做逐项映射：

- 匹配优势项：直接对应 JD 的证据。
- 待提升项：有相关经历但表述不足、成果未量化。
- 空白项：简历完全没提，且用户可能确实没有。
- 冗余项：与目标岗位无关、应删减或弱化的内容。

可以给一个总体匹配度，但要说清权重口径（必备 50% / 加分 30% / 差异化 20%），并提醒这是估计值。

### 步骤 4：改写

按 `references/writing-standards.md` 执行：

1. 顺序：最匹配的经历放前面，无关内容后移或删掉。
2. 关键词：用 JD 的行业通用词替换自造表述，自然融入，不堆砌。
3. 成果：每条尽量有数字、规模或前后对比。
4. 结构：STAR 的压缩版——背景一句话，动作和结果占主要篇幅。
5. 公司类型：大厂偏体系化与规模，中小企业偏端到端落地，初创偏从 0 到 1 与多角色。
6. 跨行业：按 `references/matching-diagnosis.md` 的能力迁移部分改写，不编造新经历。

### 步骤 5：交付

- 定制稿：岗位会话用 `job_tailored_write`，简历会话用 `resume_tailored_write`（传 jobId），都是整体覆写；主简历改写只在简历会话里用 `resume_write`，岗位工作台不能改主简历。
- 写入后给一份简短的变更说明：删了什么、重排了什么、补了哪些关键词、哪些数字还需要用户确认。
- 简历会话里可以提议 `resume_job_evaluate` 跑后台匹配度评估；岗位会话里让用户去岗位表点「简历评估」。
- 岗位表里的匹配度报告和简历的完整性报告由后台任务写入，不要手改，也不要在对话里假装已经跑过。

## 硬规则

- 不编造公司、职位、项目、数字、证书；只改表述、顺序、颗粒度。
- 不删除真实经历来「美化」；可以弱化、合并、后移。
- 不把 AI / 互联网行业的评分口径套到所有行业；非技术岗按路径 A 的方向口径调整。
- 不承诺「一定能过 ATS / HR 初筛」；只能说明关键词覆盖和可读性问题。
- 跨行业的「难度系数」只用于解释行业差异，不参与总分换算，也不作为简历好坏的结论。
