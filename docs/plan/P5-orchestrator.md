# P5 — GoodJob 编排层（orchestrator）

> 状态：2026-10-28 定稿（待实施验收）。本文件是 spec，不是实施记录；实施中的偏差回写到本文件头部。
> 上游：`docs/PRODUCT.md` §4（交互模型）、`docs/ARCHITECTURE.md` §4（AgentRuntime）与 §3（目录布局）。
> 本文使用的领域词汇：GoodJob（编排 Agent）、子 Agent、工作流（workflow）、工作流任务、
> 依赖波次、交付摘要、工作区上传（`uploads/`）、设置（基础设置 / Agent 设置）。

## Problem Statement

现在每个模块（简历 / 岗位 / 投递 / 面试 / 公司）都各自有一个懂事的 Agent，但它们互相不认识。
用户要做一件跨模块的事——"把现有岗位按匹配度排个优先级，给前三个岗位各生成一份定制简历"、
"把这批 JD 整理进岗位库并把对应的投递记录建好"——只能自己在模块之间来回跳：先在岗位页看一遍，
记下 id，再进岗位工作台逐个生成定制稿，然后去投递页建记录。每一次跳转都要他自己当调度员，
而且中途没法回头看"我到底做到哪一步了"。

与此同时，模块页里的 Agent 不敢做跨模块的事：它只拿到本模块的工具，一旦用户提出跨模块需求，
它只能回答"请到 XX 模块去做"，或者索要一堆它其实拿不到的东西。用户体感是：**这是五个工具，
不是一个助手。**

## Solution

左栏第一行变成 **GoodJob**（品牌位，🐝 + 字标），点它进入编排层：一个没有模块归属的对话。
用户在这里说目标，GoodJob 先只读盘点工作区真实数据（`workspace_overview`），再决定怎么派：

- **一件事、一个角色、没有先后依赖** → 直接派一个子 Agent（`subagent_run`），把结果拿回来综合答复。不建工作流，界面上不出现流程图。
- **两个及以上角色，或任务之间有先后关系** → 拆成工作流（`workflow_run`）。对话右侧出现工作流面板：子 Agent 数量与状态汇总、依赖流程图、选中任务的交付摘要。任务按依赖波次执行，无依赖的并行，同角色同对象的串行。

子 Agent 按角色复用各模块已有的能力与指令（简历 / 公司 / 岗位 / 投递 / 岗位工作台），
但**拿不到浏览器、通知、会话工具**——AI SDK 的 subagent 不支持 `toolApproval`，
把有副作用的动作放进去等于绕过审批门（硬约束 7）。需要联网或发邮件时，GoodJob 在答复里
如实交回用户，去对应模块操作。

用户在 GoodJob 里会上传参考文件（一批 JD、一份岗位清单、一张截图说明）。这些文件落在
工作区级的 `uploads/`；子 Agent 拿到只读的 `upload_list` / `upload_read`，能直接读同一批文件。

一次工作流的逐任务状态落盘在工作区的 `workflows/`，切模块、切对话、重启后回到这个对话
仍能看到它——除非上次是在跑的时候退出的，那时它会诚实地收起成"未完成"，而不是永远显示"运行中"。

## User Stories

1. 作为求职者，我想在左栏第一行直接看到 GoodJob（品牌位），点一下就回到 Agent 首页，这样我不用在五个模块里猜"跨模块的事该去哪说"。
2. 作为求职者，我想用一个自然语言的句子下达跨模块目标（"给匹配度前三个岗位各生成定制简历"），这样我不用先自己排好顺序再逐个模块执行。
3. 作为求职者，我想让 GoodJob 在派活之前先盘点我工作区里真实存在的简历 / 公司 / 岗位 / 投递 / 面试，这样它给子 Agent 的 id 和现状是真的，而不是编的。
4. 作为求职者，我想让 GoodJob 判断这件事该一个人做还是拆成工作流，这样简单的润色不会被拆成五个子 Agent 来回折腾（也省我的 token）。
5. 作为求职者，我想让"只需一个角色就能做完"的事直接派一个子 Agent 并当场拿到结果，这样界面不会为一个任务弹出一整块流程图。
6. 作为求职者，我想让"多个角色协作或有先后依赖"的事变成工作流，这样我能看见它被拆成了几步、每步由谁做。
7. 作为求职者，我想在右侧面板一眼看到工作流的总标题、子 Agent 数量和"运行中 / 等待 / 完成 / 失败 / 已跳过"各自多少个，这样我不用读日志就知道整体进度。
8. 作为求职者，我想在右侧面板看到一张依赖流程图（节点 = 任务，连线 = 前置关系），这样我能立刻看出哪些任务在并行、哪些在等别人。
9. 作为求职者，我想让流程图节点上显示角色（简历 / 公司 / 岗位 / 投递 / 岗位定制）、短标题和状态，这样我不用点开每个节点就能读图。
10. 作为求职者，我想点任意节点看它的交付摘要（Markdown 渲染）或错误原因，这样我能定位到底哪一步没做成、为什么。
11. 作为求职者，我想让面板默认选中"正在跑"的那个任务，这样工作流一开始跑我的视线就落在当前进展上；但我点过别的节点之后，选择不再被自动抢走。
12. 作为求职者，我想在没有选中的任务时看到一句人话（"子 agent 正在执行，完成后这里会显示它的交付摘要" / "等待前置任务完成" / "前置任务没有完成，这个任务没有执行"），这样空面板不会让我以为它卡住了。
13. 作为求职者，我想在节点详情里看到该任务声明的前置任务 id，这样我核对拆解是否合理时有依据。
14. 作为求职者，我想让没有依赖关系的任务并行执行，这样一批互不相关的岗位能同时推进，而不是排队等。
15. 作为求职者，我想让"同一角色 + 同一对象"的任务串行（两个改同一份简历的子 Agent 不会互相覆盖），这样并行不会写坏我的文件。
16. 作为求职者，我想让前置任务失败时后续任务被明确标成"已跳过"并说明原因，而不是假装成功或永远转圈。
17. 作为求职者，我想让一条分支失败时其他分支照常跑完，这样一个小错不会让我整批任务作废。
18. 作为求职者，我想在 GoodJob 提交工作流时就被挡住明显错误的拆解（重复 id、依赖不存在、任务依赖自己、依赖成环），这样我不会花几分钟等一个必然失败的图。
19. 作为求职者，我想让"只派一个任务却调用工作流"被挡住并提示直接用单 agent 派发，这样界面上不会出现一个只有一个节点的流程图。
20. 作为求职者，我想让单次工作流有任务数量上限（10）并在超出时收到"合并或分两次"的提示，这样一次派发不会失控地烧钱。
21. 作为求职者，我想让同一个 GoodJob 对话同时只跑一条工作流，并被告知"等它结束再派发新的"，这样状态机和右侧面板不会被两条流混在一起。
22. 作为求职者，我想在 GoodJob 对话里点停止时，正在跑的子 Agent 一起停下（而不是父流停了、子 Agent 还在后台烧 token）。
23. 作为求职者，我想让单个子任务有独立超时（5 分钟）、整条工作流有总预算（30 分钟），这样某个子 Agent 卡死不会拖住整条工作流。
24. 作为求职者，我想让子 Agent 执行期间 GoodJob 的流式看门狗被持续续命，这样长时间的子任务不会被误判为网关卡死而中断。
25. 作为求职者，我想让每个 GoodJob 对话只保留最近一次工作流，并在切回这个对话时自动恢复它的状态，这样我不必担心历史工作流把面板搞乱。
26. 作为求职者，我想在切工作区时让正在跑的工作流停止，并且不会把上一个工作区的状态写进新工作区，这样两份工作区的数据不会串。
27. 作为求职者，我想在"上次是运行中退出的"工作流重新打开时看到它被收成"未完成"（跑着的任务记失败、没跑的任务记已跳过，各带一句原因），这样面板不会永远显示"运行中"骗我。
28. 作为求职者，我想在 GoodJob 对话里上传一批参考文件（JD 原文、岗位清单、旧简历），这样我不用先自己拆散内容再分给各个模块。
29. 作为求职者，我想让子 Agent 能只读我看到的那批上传文件（`upload_list` / `upload_read`，PDF / Word 自动抽纯文本），这样拆解时不用把原文整段抄进任务说明。
30. 作为求职者，我想让 GoodJob 在任务说明里既写清要用的文件名、又带上关键原文要点，这样后置任务不必重新翻一遍附件。
31. 作为求职者，我想让模拟面试会话也能上传参考资料并让面试官读到，这样我准备的背景材料在两处都能用。
32. 作为求职者，我想让子 Agent 明确知道自己没有浏览器 / 邮件 / 会话工具，并在结果里说明"需要联网但因为没工具没做"，这样它不会假装查过。
33. 作为求职者，我想让子 Agent 不向我提问、不等我确认（它看不到我的对话），信息不足时保守完成并在摘要里列出缺口，这样工作流不会卡在一个没人能回答的问题上。
34. 作为求职者，我想让子 Agent 的最终回复是一段可转述的摘要（先结论、再关键事实与产出位置、最后风险与未完成项），这样 GoodJob 能把它综合成一段我能直接执行的答复。
35. 作为求职者，我想让 GoodJob 在收尾时如实说明哪个子 Agent 失败 / 被跳过、哪些能重试，而不是编造成功，这样我对产出的信任不被一次谎话破坏。
36. 作为求职者，我想让 GoodJob 不做具体业务操作（不亲自改简历、不亲自建投递），这样职责边界清楚：它的问题永远是"这件事该谁做"。
37. 作为求职者（未配置模型时），我想让 GoodJob 明确告诉我 `llm_not_configured` 并引导去设置，这样它不会拿一段假数据糊弄我。
38. 作为开发者，我想让子 Agent 的角色集合封闭（resume / companies / jobs / applications / job 五种），这样新增能力只能通过已存在的模块边界，不会长出第二套并行实现。
39. 作为开发者，我想让 `job` 角色的任务必须带岗位 id 且该岗位必须真实存在，其余角色禁止带 id，这样角色契约不会含糊。
40. 作为开发者，我想让工作流状态在每次变化（任务进入运行 / 完成 / 失败 / 跳过、整体状态变更）时推给渲染层并落盘，这样界面与磁盘不会各说一套。
41. 作为开发者，我想让落盘失败不打断运行（内存里仍有完整状态、界面继续更新），这样磁盘满或权限异常时用户的工作不白做。
42. 作为开发者，我想让事件与快照按 `updatedAt` 取较新的一份，这样挂载时拉快照与订阅增量的竞态不会把状态回退。
43. 作为开发者，我想让工作流快照以 `0600` 落在工作区的 `workflows/`、以 encodeURIComponent 后的会话 key 命名，这样多线程对话（`scope#threadId`）不会互相覆盖。
44. 作为开发者，我想让子 Agent 用独立上下文（各自一套指令 + 各自一套工具），这样它们的中间过程不会污染 GoodJob 的上下文预算。
45. 作为开发者，我想让子 Agent 的输出回灌 GoodJob 时被截断到上限（12K 字符）并标注已截断，这样一批子 Agent 不会一次性撑爆父上下文。
46. 作为开发者（写测试的人），我想让整条编排逻辑可以在不启动 Electron、不联网的情况下被驱动（模型替身 + 临时工作区），这样 CI 里能跑、且不会碰真实数据。
47. 作为开发者，我想让工作流的核心规则（图校验、波次调度、同角色串行、跳过传播、中断收尾）由一份冒烟脚本覆盖，这样后续改动不会悄悄破坏它们。

## Implementation Decisions

### 模块与边界

- **新增会话场景 `orchestrator`**：进入 `ConversationScope`，有独立指令、独立工具集、独立上传目录（工作区级 `uploads/`），并成为左栏第一个模块（品牌位）。它不做业务写操作。
- **新增 `WorkflowService`**（main，`agent/workflow.ts`）：编排层唯一的执行入口。两个公开动作：
  - `runSubagent(role, title, instruction, targetId?, signal?)` → 单角色一次性任务，**不产生工作流**，结果同步返回给工具调用。
  - `runWorkflow({key, title, tasks, signal})` → 建工作流、按依赖波次执行、落盘并推送状态，返回逐任务结果。
  - 另有两个生命周期动作：`get(key)` 取当前对话最近一次工作流（含中断收尾），`abortAll()` 停止所有在跑的子 Agent；`useWorkspace(paths)` 在切工作区时停掉旧任务并丢弃旧状态。
- **新增编排工具注册表**（`workspace_overview` / `subagent_run` / `workflow_run`），只在 `orchestrator` 场景注册。模块会话的工具集不变。
- **子 Agent 工具集装配**：按角色复用对应模块的业务工具 + 只读上传工具 + 该角色适用的技能索引。**明确不含** 浏览器 / 通知 / 会话 / 记忆工具，理由写进代码注释与文档：AI SDK 的 subagent 不支持 `toolApproval`，副作用动作会绕过审批门。
- **`AgentDeps` 增加 `workflow`**（getter 形式剪断 WorkflowService ↔ AgentDeps 的构造顺序循环）。`AppContext` 增加 `workflow`，`IpcDeps` 同步。
- **`AgentRuntime` 两处接口变化**：`trackFor` 等工具装配入口接受一个"续命"回调（子 Agent 期间重置 90 秒首字节看门狗）；`abort()` 额外调 `workflow.abortAll()`（子 Agent 跑在 tool execute 里，不在 running 表里）。

### 图与调度语义

- 角色集合封闭：`resume | companies | jobs | applications | job`。`job` 必须带 `targetId` 且该岗位存在；其余角色带 id 直接报错。
- 任务 id：1–32 位 `[A-Za-z0-9_-]`。`title`、`instruction` 非空。`dependsOn` 去重。
- 建流时校验图：id 唯一、依赖必须存在、不能依赖自己、**无环**（Kahn 拓扑排序，报错时给出环上的 id 列表）；任务数 `< 2` 时拒绝（"只有一个任务时不要建工作流"），`> 10` 时拒绝。
- 同一对话同时只允许一条运行中的工作流（冲突时明确提示等它结束）。
- 执行循环（每次迭代）：①把"前置失败 / 被跳过"的 pending 任务标 `blocked` 并写原因；②取"所有前置都 done"的 pending 任务作为本波；③本波内按 `role:targetId` 分组，**组内串行、组间最多 3 组并行**；④无障碍则收尾。
- 收尾：所有 pending 落 `blocked`；整体状态 = 全部 `done` → `done`，否则 `failed`。
- 状态机（来自原型 `src/main/agent/workflow.ts`，此处只保留决策密集部分）：
  - 任务：`pending → running → done | failed`，以及任意 pending → `blocked`（前置失败 / 工作流中止）。
  - 工作流：`pending | running | done | failed`。
- 超时与预算：单子任务 5 分钟；整条工作流 30 分钟（所有任务共享）；子任务流式期间每 20 秒续命一次看门狗；子 Agent 输出截断到 12 000 字符并标注"输出过长已截断"。
- 子 Agent 的执行：`ToolLoopAgent` + 该角色的指令 + 该角色的工具 + `stepCountIs(20)` + 输出上限取 `min(模型上限, 32K)`；一次性 `generate`，不流式给用户。

### 持久化与 IPC

- 落盘位置：`<workspace>/workflows/<encodeURIComponent(key)>.json`，`0600`，整文件覆盖。一个 GoodJob 对话只留最近一次工作流。
- `get(key)` 若读到 `status === "running"`：把 running 的任务记失败（"应用退出或工作区切换，任务被中断。"）、pending 记 `blocked`（"工作流中断，任务未执行。"），整体收成 `failed` 并立即回写——**重启后不留假的"运行中"**。
- 渲染层用 `0600` 读到的任何字段都要能容错：`reviveWorkflow` 逐个字段做类型校验，未知角色 / 未知状态 / 缺失数组一律降级而不是抛错。
- 新 IPC：`workflow:get`（`invoke`，入参会话 key）与 `workflow:event`（`send`，推送整份 `WorkflowState`）。preload 暴露 `window.goodjob.workflow.{get, onEvent}`；`src/shared/types` 与 preload 同步更新（硬约束：改 IPC 三处一起改）。
- `commit()` 的丢弃规则：切工作区 / 旧工作流收尾时，`active` 已被清掉且缓存已换过 → 直接丢弃这次提交，避免把旧工作区状态写进新工作区。

### 渲染层

- **左栏品牌位**：模块注册表增加 `brand: true` 的 `orchestrator` 项（🐝 + `GoodJob` 字标），渲染成菜单第一项；一列只出现一次 GoodJob（不再另起一行品牌标题）。默认模块与首个常驻模块都变成 `orchestrator`。
- **`OrchestratorPage`**：`ConversationPane`（scope = `orchestrator`）+ `ChatPanel`。空状态文案要说清"我会先判断该由谁做"。
- **右侧工作流面板**：只有 `WorkflowState` 非空（即真的建了工作流）才出现，用 `ResizablePanelGroup` 与对话并排（对话最小 420、面板最小 320）。面板 = 头部（标题 + 整体状态徽标）+ 汇总（任务数 + 各状态计数）+ 依赖图 + 选中任务详情。
- **依赖图布局不引第三方图库**：按"最长路径分层"计算层级，同层水平居中排开，节点固定尺寸，连线用 SVG 三次贝塞尔；容器溢出时横向滚动（侧栏窄，这是刻意的取舍）。
- **状态色只用 `globals.css` 的 token**（`primary` / `success` / `destructive` / `border` / `muted`），浅色与深色都要成立。
- **订阅逻辑独立成 hook**：挂载 / 换 key 时拉一次快照，之后增量合并；`null` 快照表示"这个对话没有工作流"，保持不渲染面板；快照与事件按 `updatedAt` 取较新的（防竞态回退）。
- 交接给渲染层的 `ChatPanel` 增加 `emptyTitle` / `emptyDescription` / `placeholder` 等文案入口，让编排层的空状态说自己的话，而不是复用模块页的文案。

### 指令（prompt 层）

- GoodJob 指令的核心是**判断**而不是执行：一个人做还是拆工作流、先 `workspace_overview` 拿真实 id、单条工作流 ≤ 10 个任务、依赖只写真的需要等的、有依赖的任务不能假设后置任务看见了前置输出。
- 子 Agent 指令在模块指令之上叠一段硬规则：只完成本次任务、不提问不等待、只读上传工具、没有浏览器 / 通知 / 会话工具、不越界建数据、结尾给"结论 → 事实与产出位置 → 风险与缺口"的可转述摘要。
- GoodJob 不注入技能索引（否则场景判定会把它当作简历会话）。

### 设置与上传的连带改动（只写与本特性直接相关的部分）

- 上传目录按会话 key 解析，`orchestrator` → 工作区级 `uploads/`；删除"模拟面试会话不给上传工具"的旧特例（面试官现在也拿到只读上传工具）。
- 会话上传目录、`WorkspacePaths` 新增 `workflows/` 与 `uploads/` 两项，并在 `ensureWorkspaceDirs()` 里建好（硬约束：新路径先登记再建目录）。

## Testing Decisions

**什么算好测试（本特性的标准）**

- 只测**外部可观察行为**：给定一组任务图与一组子 Agent 产出，工作流最终的逐任务状态、整体状态、落盘内容、`get()` 在重启路径上的结果是什么。不测私有方法怎么实现、不测循环内部顺序、不断言日志字符串。
- 一次性判定只断言"用户能看见的那句话"（例如"任务被跳过"的原因必须出现），不断言完整错误文案。
- 不测模型：子 Agent 的产出是替身。测的是编排规则，不是 prompt 质量（prompt 质量靠人工走查，不进 CI）。
- 不碰真实工作区：全部在 `mkdtemp` 的临时目录里跑，不读 `~/.goodjob`。

**命名与选择的接缝（一个）**

- **唯一接缝：`WorkflowService` 的公开 API** —— `runWorkflow` / `runSubagent` / `get` / `abortAll` / `useWorkspace`。这是整个特性最高、也是唯一必要的接缝：图校验、波次调度、角色串行、跳过传播、超时中断、落盘与复活全部在这条边界的一侧；渲染层与 IPC 只是把它的状态搬出去（IPC 契约由类型检查覆盖，面板取值逻辑靠 `updatedAt` 的纯函数式合并规则由 UI 冒烟覆盖，不进本次自动化范围）。
- 模型替身插在同一层：`WorkflowService` 通过 `createLanguageModel` 取模型，测试里把它替换成 AI SDK 官方的 `MockLanguageModelV4`（`ai/test`），按角色返回不同的假摘要——这样"谁调了模型、调了几次、拿到什么摘要"都可断言，而不需要网络或 API Key。
- 依赖装配用**假 `AgentDeps`**：只实现 `WorkflowService` 真正用到的部分（`models.resolveActive`、`jobs.get`、`memory.read`、`uploadDir`、各模块工具依赖）。这样测试不启动 Electron，也不需要 `?raw` 引用的技能库被 Vite 处理。

**要覆盖的行为清单**

1. 图校验：重复 id / 依赖不存在 / 自依赖 / 成环（报错里带环上 id）/ 任务数 < 2 / 任务数 > 10 / id 字符非法 / `title`、`instruction` 为空。
2. 角色契约：`job` 缺 `targetId`、`job` 的 `targetId` 不存在、非 `job` 角色带 `targetId` 都要拒绝。
3. 波次调度：三层依赖的图按 0 → 1 → 2 层推进；同波无依赖任务并行；同波同角色同对象串行（用假模型的可观测调用顺序断言）。
4. 跳过传播：一条分支前置失败 → 该分支后续任务 `blocked` + 原因；另一条独立分支仍跑到 `done`；整体状态 `failed`。
5. 整体状态：全 `done` → `done`。
6. 同一对话并发：第二次 `runWorkflow` 在第一次未结束时被拒绝。
7. 单 agent 不建工作流：`runSubagent` 之后 `get(key)` 仍是 `null`。
8. 落盘与复活：跑完后文件存在、权限 `0600`、内容可被新实例 `get()` 读回（含中文、含 `targetId`、含 `dependsOn`）。
9. 中断收尾：手工把落盘文件改成 `running`（模拟上次退出），`get()` 后 running 任务记失败、pending 记 `blocked`、整体 `failed`，且回写磁盘。
10. 中止：`abortAll()` 让运行中的任务落 `blocked` / `failed` 且整体不是 `done`；工作流结束后再调用不抛错。
11. 切工作区：`useWorkspace(otherPaths)` 后旧 key 的 `get()` 为 `null`，且旧工作流的收尾提交不会写进新工作区目录。
12. 输出截断：子 Agent 返回超长文本时 `summary` 带截断标注。

**Prior art（本仓库已有同类测试）**

- `scripts/p4-agent-guard-smoke.mjs`：用 `jiti` 直接跑 `src/main` 的 TS 源码、`electron` 走 stub、`node:assert/strict` 逐条断言，不启动窗口、全程无网络。本特性的冒烟脚本沿用这套骨架（`scripts/` 下同风格的新脚本）。
- `scripts/p3-interviews-store-smoke.mjs` / `scripts/p3-notify-service-smoke.mjs`：临时工作区 + `workspacePaths()`/`rootPaths()` + 真 store 落盘 + 0600 权限断言 + "新建实例从磁盘复活"的写法，正是本特性第 8、9 条要复用的模式。
- `scripts/p2-ui-smoke.mjs` / `scripts/p3-ui-smoke.mjs`：CDP 驱动渲染层、浅色 / 深色各截图一次——工作流面板的视觉验收沿用这个方式（一次性、不入构建）。

## Out of Scope

- **设置全部搬到配置根目录**（`RootPaths` / `models.json` / `notifications.json` / `agent-browser.json` / `browser-playbooks.md` 的位置与"设置全局通用"的语义）以及设置弹窗重构为「基础设置 / Agent 设置」两组。这是同一工作树里的另一件事，单独出 spec。
- 子 Agent 使用浏览器 / 通知 / 上传写操作。受 `toolApproval` 与硬约束 7 限制，本轮明确不给；将来如果 AI SDK 支持 subagent 审批流再议。
- 工作流的历史（同一对话的历次工作流列表）与跨对话的工作流总览。现在一个对话只留最近一次。
- 断点续跑：应用退出 / 切工作区后工作流不续跑，只把状态收成为终态（结果已落库，可重新派发）。
- 用户在面板上编辑 / 重排 / 重试单个任务（"只重跑这一步"）。重试目前只能由用户让 GoodJob 重新派发。
- 工作流中间过程的流式展示（不展示子 Agent 的思考与工具步骤，只展示状态与最终摘要）。
- 语音面试（P3 M2）、日报内容改版等与编排层无关的既有后置项。
- 右上角任务角标（`TasksBadge`）是否要显示工作流进度——本轮不动。
- 工作流节点的手工拖拽布局 / 自动排布库。

## Further Notes

- **为什么右侧面板不是"卡片里的折叠把手"**：按界面结构约定，收起 / 展开只在顶栏，卡片内部只放内容自身的控件；工作流面板是内容块之一，所以它内部只有图与任务详情，不提供"收起整个工作流"的开关。
- **为什么面板是条件出现而不是常驻**：单 agent 任务占多数，常驻一个空面板会持续暗示"你应该拆任务"。条件出现把"拆了没有"变成可见的信息。
- **和模块 Agent 的边界**：模块 Agent 仍然是该模块的第一入口（简历页的对话仍然是改简历最快的地方）。GoodJob 是**跨模块**的入口，不是模块 Agent 的替代品；指令里明确它不亲自做业务，避免用户发现"简历页和 GoodJob 说法不一致"。
- **成本**：一条工作流最多 10 个子 Agent，每个最多 20 步。这是刻意的上限——一次派发 ≈ 10 次完整会话。任务说明要求自带上下文，也是为了让子 Agent 不必反复翻附件（省 token 也省时间）。
- **已知的粗糙处**（实施时应记录，不阻塞）：子 Agent 的角色串行按 `role:targetId` 分组，同一角色改不同岗位工作台之间可以并行——如果将来出现"同一份主简历被两个 `resume` 任务改"，分组键要重新考虑。
- **主进程产物**：技能库以 `?raw` 内联，只有 `pnpm build` 能解析；`jiti` 直跑 `workflow.ts` 会因 `.md` 扩展名失败。写冒烟脚本时必须绕开技能库的实际加载（见 Testing Decisions 的"假 AgentDeps"）。
- 验收入口沿用仓库既有约定：`pnpm typecheck` + `pnpm build` 必须干净；界面改动浅色 / 深色各看一眼；新增持久化目录同步更新 `AGENTS.md` 的「工作区」一节与 `paths.ts` 的注释。
